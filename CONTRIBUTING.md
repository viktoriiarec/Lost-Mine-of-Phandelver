# Правила разработки

## Рабочий цикл

1. Выбрать одну небольшую задачу с проверяемым результатом.
2. Создать ветку от актуальной `main`.
3. Реализовать задачу без несвязанных изменений.
4. Проверить компиляцию Unity и относящиеся к задаче тесты.
5. Открыть pull request с результатом и способом проверки.
6. После проверки объединить изменения в `main`.

## Когда задача готова

- проект компилируется без ошибок;
- поведение воспроизводится по короткой инструкции;
- игровые правила не находятся в UI;
- чистая логика покрыта тестами;
- новые сторонние ассеты внесены в `THIRD_PARTY_NOTICES.md`;
- документация обновлена, если изменилось поведение.

## C# и Unity

- Пространство имён: `HeartOfDepths` и вложенные пространства.
- Один основной публичный тип на файл.
- `PascalCase` для типов, методов и свойств; `camelCase` для параметров и локальных переменных; `_camelCase` для приватных полей.
- Не хранить изменяемое состояние сессии в ScriptableObject.
- MonoBehaviour отвечает за жизненный цикл Unity; правила по возможности остаются в обычных C#-классах.
- Не использовать глобальные менеджеры без конкретной ответственности.
- Диалог, бой, сохранение и UI развиваются как отдельные модули.
- Ссылки Inspector проверяются в `Awake` или `OnValidate`.

## Коммиты

Формат: `type: краткое действие`.

Примеры:

- `feat: add character check resolver`
- `fix: prevent integrity below zero`
- `docs: describe vertical slice`
- `test: cover partial success threshold`

Типы: `feat`, `fix`, `docs`, `test`, `refactor`, `chore`.

## Pull request

Указать:

- что изменилось;
- зачем это нужно;
- как проверить;
- известные ограничения;
- скриншоты для визуальных изменений.
